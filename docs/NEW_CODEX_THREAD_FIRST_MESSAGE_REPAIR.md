# 新建 Codex 对话首条消息误入排队修复

## 现场与原因

- 新建 Codex 对话后，第一条消息于 2026-10-15 00:35 UTC 被标记为 `unverified`，队列中没有更早的消息或阻塞项。
- 服务日志显示 `thread/start` 成功；随后首条消息发送前的 `thread/resume` 返回 `no rollout found for thread id`。该线程尚未产生历史文件，因此这次失败发生在 `turn/start` 之前。
- 发送路由总是把工作目录交给 `CodexAppServer.start_turn()`，后者只要收到工作目录便调用 `resume_thread()`，导致刚建立且仍驻留在 app-server 内存中的线程被错误恢复。
- 该条消息的历史文件不存在；现有 `unverified` 记录应保留，不自动重发，避免未来出现重复发送。

## 实施步骤

1. 记录由当前 app-server 创建、尚未成功启动首轮的线程及初始工作目录。首次发送直接对该线程调用 `turn/start`，并把当前工作目录作为参数传入；已有历史的线程继续原有恢复流程。
2. 首轮确认启动后移除临时标记；app-server 进程重建时清除标记，避免把失效的内存线程当成仍可发送。
3. 若提交结果为待确认，前端明确显示送达状态，避免把这类首轮失败仅表现为普通排队。
4. 更新修复版本与简要版本记录，检查改动范围后仅提交本地仓库。保留用户现有 Android 开发文档修改；不主动重启当前正在服务的后端。

## 生效边界

运行中的 Python 后端在启动时加载代码；本次代码修改不会自动进入现有进程。当前那条未确认消息需要在可控切换后按历史记录核对，不能在未确认送达情况前自动发送。

## 检查记录

- 本机 Codex app-server 生成的 `TurnStartParams` 协议定义包含 `cwd`，可在首轮发送时直接指定工作目录。
- 仅执行静态改动检查；本次未运行测试，也未重启运行中的后端。
