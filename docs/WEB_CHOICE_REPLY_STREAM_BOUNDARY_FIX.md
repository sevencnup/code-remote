# 网页回答选择卡片后旧回复重复修复

## 问题与分类

用户回答选择卡片后，新回复会再次拼入回答之前的助手正文和代码块。会话原始记录中，旧正文、用户回答和新回复按顺序各出现一次；这些消息可以属于同一个运行中的 turn。

共享排队发送路径在等待本地请求确认时跳过了用户 item 事件，导致助手流未在用户回答处结束。历史读取和旧的渲染回调随后可能把回答前的正文再次带入回答后的气泡；仅按 turn ID 或复用气泡 ID 无法区分这两个回复段落。

分类为修复 / PATCH，目标版本 `0.87.3-dev.1`：恢复已有快速回答和跨网页同步的正确顺序。

## 实施步骤

1. 提取可独立检查的流式消息合并逻辑，添加复现同一 turn 内用户回答分界的回归用例。
2. 本地发送等待确认时仍处理用户 item；只在真正的新用户消息处结束上一段回复，并使旧历史请求失效。
3. 拒绝缺少已显示用户回答的旧历史快照，禁止跨用户消息复用助手气泡，忽略已结束回复段落的迟到 item。
4. 覆盖历史恢复、连续回答、重复事件、发送确认先后顺序，执行相关测试并构建 `4173` 页面产物。
5. 更新版本与简要版本记录，检查差异并提交到本地仓库。

## 补充边界处理

- HTTP 已确认发送但 turn 回执尚未到达时，仍结束当前回复；用户消息保留未知 turn 状态，等待真实回执，不猜测归属。
- 已接受、尚未提交到 React 视图的用户消息参与去重和历史检查，避免同一批事件中重复结束回复。
- 已绑定服务器 item 的本地消息不会再次匹配后续相同内容的回答；旧 ID 与实时消息别名一并参与发送去重。

## 验收标准

- 回答后顺序为旧回复、用户回答、新回复，旧正文及代码块只保留一份。
- 连续回答、共享排队确认以及另一网页的同轮输入都不会把旧回复带回。
- 延迟的历史快照或旧 item 不会重新打开上一段回复。
- 合法的新回复即使文字与旧回复相同，也应保留。
