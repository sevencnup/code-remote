# 排队消息恢复顺序修复开发记录

## 目标

避免开发热更新、页面刷新或网络恢复后，排队消息因客户端缓存误判空闲而抢在原 Codex 回复完成前启动；未正常完成的上一轮不应自动放行队列。

## 已确认风险

- 排队消息会持久化，但它等待的活动 turn ID 和完成状态没有一起持久化。
- 恢复时缓存命中可能提前将队列标记为可发送，未必经过本机 Codex 的实时历史确认。
- `turn/completed` 的活动/非活动会话分支以及恢复 effect 都可能直接启动队首；部分路径没有统一检查恢复屏障。
- 已停止或失败的 turn 也会被当作普通完成处理并自动发送队列，可能打断用户原本尚未完成的工作。

## 实施步骤

1. 为每个有待发队列的会话持久化恢复屏障及其等待的 turn ID；升级前已有的队列默认进入待验证状态。
2. 页面恢复时，存在队列的会话必须读取本机 Codex 的权威线程状态，不能仅凭历史缓存放行；运行中、失败、停止或状态不确定时保持阻塞。
3. 将自动队列推进集中到统一守卫：活动 turn 未结束或恢复屏障未解除时，所有 effect、完成事件及普通发送重试路径均不得启动新 turn。
4. 只有对应 turn 正常完成，或权威历史明确确认最新 turn 正常完成/不存在 turn，才解除屏障并按 FIFO 顺序发送；失败或停止后保留队列，供用户手动处理。
5. 增加纯逻辑回归测试，更新版本记录，运行相关测试、前端构建和差异检查后创建本地 Git 提交；不推送 GitHub。

## 验收标准

- 热更新/刷新后，Codex turn 仍运行时队列不会自动发送。
- 缓存显示空闲但本机 Codex 报告仍运行时，队列继续等待。
- 正常完成后队列按原顺序逐条发送，不重复或并发启动。
- turn 被中断、失败或无法确认状态时，队列保留且不抢发。
- 旧版本遗留队列恢复时先进行权威状态校验。
- 相关测试、`pnpm build` 与 `git diff --check` 通过。
