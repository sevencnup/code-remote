# 移动端持续大流量同步修复

## 目标与分类

解决手机长期使用后仍下载大量重复数据的问题。按修复 / PATCH 处理，保留消息、排队送达、操作记录和断线恢复的完整性。

## 实施步骤

1. 检查正在提供服务的版本、历史同步触发条件、WebSocket 消息投影、传输缓存与移动端后台行为；只统计请求和数据体积，不输出聊天正文或认证信息。
2. 根据实际请求记录和代码路径定位重复下载；统计会话摘要和历史投影的大小，不读取或输出认证信息。
3. 修复已确认的重复同步或缓存失效原因，避免用丢弃消息、操作记录等方式减少流量。
4. 复查同步与缓存边界，完成生产构建，记录测量结果和生效条件；本次不新增或运行测试。
5. 更新版本及简短版本记录，创建本地提交；保留已有 APK 文档修改。

## 验收标准

- 无变化会话不会持续下载完整历史；多窗格、重连和后台恢复不会扩大重复同步。
- 活动回复主要传输新增内容，历史和工具记录仍可完整查看。
- 历史缓存超出内存预算时具有明确的可复用策略，不会默默退化成每次全量。
- 说明实际验证范围、尚需真机观察的部分及后端变更的加载方式。

## 排查记录（2026-10-15）

- 修复前的服务日志采样：20 分钟内，会话列表接口返回 200 共 841 次，具体会话历史接口返回 200 共 9 次。此为所有连接的合计，不能直接算成某一台手机的用量。
- 本机 96 条 Codex 会话摘要投影合计 35,597 字节，gzip 后 12,033 字节；该离线统计不含运行时合并项、Claude 会话、HTTP 头或 WebSocket，因此不是手机实际流量计量。
- 按本机原始历史文件大小取前三条，其浏览器历史投影约 4.43、2.47、3.43 MB，gzip 后约 1.69、0.65、1.62 MB；尚未进行图片补全。可确认完整历史重读具有明显成本，不能把全部日流量归因于某一个接口。
- 文件与数据库 WAL 变更触发通用通知，原来只有 1 秒防抖。每个窗格都可能在请求结束后再次完整拉取列表。
- 页面隐藏后仍处理列表刷新；Android 已发送后台事件，聊天同步层此前没有监听。网络不稳定时，后台还会持续重连、恢复历史。
- 原来的增量传输基线只存在内存；单条 JSON 超过 8 MiB 就不保留，页面重载也会失去基线。已有 UI 缓存无法替代该传输基线。

## 本次修改

1. 自动列表请求共享 15 秒缓存并合并在途请求；变更通知使用有频率上限的尾部刷新。手动刷新和明确的聊天管理操作保留及时更新，实时回复继续由 WebSocket 推送。
2. 监听浏览器可见性与 Android 后台/恢复事件。后台取消在途历史和列表下载，暂停自动同步与断线重试，取消聊天详情订阅；连接存活时继续接收完成和审批通知。排队发送仍由服务端管理。
3. 为暂停订阅、断线留下的消息缺口单独做标记，恢复连接后补齐；回复完成或切换聊天不能提前消除该标记，也不能把缺失内容的 UI 存成完整缓存。
4. 使用已有 fflate 依赖在 Worker 中压缩历史同步基线。压缩内存缓存上限 8 MiB / 5 条，IndexedDB 的独立 transport 存储区上限 50 MiB / 5 条；原 UI 存储区保留，不相互挤占条目。刷新页面、缓存超出内存预算时仍可读取持久化基线进行增量同步。
5. 缓存只用于合并通过认证的服务端响应；合并版本不符时保留完整响应回退。配额不足、超出压缩磁盘预算、缓存淘汰、旧后端没有增量协议或后端丢失对应版本时仍可能完整读取，不能承诺所有历史下载都变为增量。
