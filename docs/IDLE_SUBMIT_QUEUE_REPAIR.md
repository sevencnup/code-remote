# 空闲发送误显示排队与启动延迟修复

## 现场核查

- 当前后端已重新启动，并已加载上一版提交接口；不能归因于旧进程。
- 共享数据库当前没有待发消息或阻塞项。两条现场消息的客户端创建时间与服务端送达回执相差约 32 秒、18 秒，最终均已送达；跨设备时间差不能直接当作后端耗时。
- 现有提交接口不区分空闲发送与真正等待，先广播入队，再完整读取历史、恢复会话、启动回复；准备发送也被展示为“已排队”。
- 启动前还会采集工作区快照；本机只读测量约 3.6 秒。完成回复时的文件差异处理也同步占用 Codex 消息读取通道。

## 实施步骤

1. 在同一会话锁内完成持久化提交与发送判断，区分“判定中 / 正在发送 / 等待 / 送达待核对”；只有真正等待及需要核对的消息显示在队列中。保留幂等回执、编辑占线及 FIFO。
2. 空闲提交优先使用不带历史的会话状态；已加载的空闲会话无需重复恢复。用明确的结束状态校正过期活动轮次，但不能清除查询期间新启动的轮次。
3. 完成事件及时释放运行状态和传输通道，文件差异后台收尾，避免下一条发送被上一轮审核阻塞；收尾必须绑定原来的文件监视器，不能拿走下一轮的监视器。
4. 补充回归测试：空闲发送全过程无假排队、真实运行仍排队、过期忙碌状态恢复、并发重试不重复发送、编辑和未知送达不被绕过、慢审核不阻塞消息响应。
5. 运行后端测试、前端测试、构建及差异检查；记录版本并仅提交本地仓库。保留用户已有 Android 文档修改。

## 运行生效边界

当前助手运行在此 Python 后端启动的 Codex 子进程内。不得为加载补丁而在修改过程中杀掉该后端或其他正在运行的会话；测试与运行服务是否已加载新版本必须分别说明。

## 验证记录

- 空闲提交在状态判定、启动及完成的全部事件快照中不出现 pending；真正忙碌的会话保持 pending，编辑及未知送达仍会阻止后续消息越过队首。
- 确认已结束的轮次可解除残留忙碌状态；查询期间的新轮次及较晚到达的启动回包不会被误清除或重新占线。
- 慢文件审核不阻塞完成通知和后续 JSON-RPC 回包，也不会收走下一轮的监视器。
- 对现场长会话通过独立、只读的临时 Codex 连接测量：状态摘要约 1 KB / 5 ms，完整历史约 4.1 MB / 206 ms。此测量验证协议与传输缩减，不代表运行服务的端到端发送耗时；临时连接已关闭。
- 前端 91 项、后端 75 项测试及生产构建通过。没有新增依赖、修改正在运行的队列数据或推送 GitHub。
