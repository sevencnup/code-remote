# 聊天历史新鲜度与跨端同步修复

## 目标与分类

修复网页和 Android 反复显示已结束回复、漏掉最近用户消息和同步延迟的问题。属于 PATCH：恢复既有聊天同步的正确性与及时性。开发期间仓库已合入独立的群聊功能，基础版本升至 `0.52.0-dev.1`，因此本次修复版本顺延为 `0.52.1-dev.2`，Android `versionCode 312`；保留已生成的 `0.50.1-dev.1` 和 `0.52.1-dev.1` 安装包。

## 实施步骤

1. 核对运行服务与工作目录，量化当前聊天的 JSONL、SQLite 投影与 API 返回之间的差异及读取耗时。
2. 修正服务端使用落后历史投影的逻辑，确保返回的内容、完成状态及版本标记来自一致的数据范围，同时保持长聊天读取有界。
3. 检查网页和 Android 的历史合并、实时消息与完成事件处理；修复已确认的覆盖和重复路径。
4. 为落后投影、遗漏完成事件和旧历史覆盖实时消息增加有实际行为断言的回归测试，运行相关测试及构建。
5. 更新版本记录，重载本机服务，构建独立 APK 并覆盖安装手机，检查实际历史读取与启动状态。验证不发送测试聊天。
6. 清理临时调试进程，执行 diff 检查并本地提交，不推送 GitHub。

## 验收

- 小于 64 MiB 的投影滞后也不能隐去最新消息或完成状态。
- 长聊天的最近历史与真实日志尾部一致，后续增量读取不回退到更旧的窗口。
- 已收到的用户消息和助手回复不被落后的历史回包清空或重复创建。
- 记录真实读取耗时；区分已完成的自动验证与尚未观察到的自然实时消息验收。

## 已确认原因与修复

- 当前聊天原始 JSONL 约 1.158 GB。网页增量接口原先仍先全量解析日志；现改用 SQLite 投影和按 item 更新序号缓存的精简内容。
- 投影原先允许落后 64 MiB，仍标记为当前日志版本。现将投影读取放在同一事务内，并重放其偏移之后的完整 JSONL 记录；半行数据等下一次写完再读取。
- 服务端对当前订阅的聊天发送轻量历史变化通知，按版本去重。两端合并频繁通知，并在读取期间有新变化时补一次读取。
- 网页不再因正在回复而跳过历史补同步；重连不再用旧缓存覆盖当前已经显示的消息；不同轮次不复用同一份流式文字。
- 网页和 Android 保留已经确认的轮次完成状态，防止旧回包或迟到事件重新启动计时。Android 将通知状态更新统一到主线程，并拒绝跨越启停事件的旧回包。
- Android 用户消息通过事件立即显示，历史随后按 item ID 去重；列表更新不再覆盖完整聊天的状态，并对历史版本变化安排正文刷新。
- 无可见内容变化时，网页跳过消息区重建。Android 列表通知合并为最多约每 5 秒一次，并以 30 秒前台元数据检查兜底，不在后台反复拉取完整历史。
