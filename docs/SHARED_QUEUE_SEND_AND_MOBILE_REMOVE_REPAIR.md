# 共享排队消息即时操作与空闲发送修复

## 目标

移动端删除排队消息后立即从界面消失；空闲会话的新消息由服务端原子判断并直接启动，运行中的会话继续安全排队。模型、思考强度和授权设置仍按现有设备本地/会话本地规则保存，本次只核实并说明，不擅自改变同步范围。

## 实施步骤

1. 核查移动端删除的往返链路、共享队列事件刷新竞争，以及空闲发送路径的服务端状态判断和防重机制。
2. 删除操作先在当前设备隐藏目标消息；服务端确认后采用返回的权威队列，失败或送达不确定时重新拉取并恢复真实状态，防止较早的刷新结果把消息闪回。
3. 增加统一提交接口：先持久入队，再在同一请求中由服务端判定空闲并尝试直接启动队首；运行中、队首被编辑或已有更早消息时保持 FIFO 排队。重试沿用同一消息 ID 和送达回执，不能重复发送。
4. 前端改用统一提交接口；成功直接发送时刷新当前会话，仍在排队时及时更新队列，不依赖手机本地的旧运行状态决定是否启动。
5. 补充客户端与服务端测试，执行完整前端测试/构建、相关后端测试和差异检查；记录版本描述并仅提交本地 Git。

## 验收

- 手机点删除后目标立即消失；删除失败可恢复，其他设备最终看到相同结果。
- 服务端确认空闲且无更早待发消息时，提交消息直接启动 Codex 回复，不显示长期等待队列。
- 正在回复、已有排队项或排队项在编辑时，新消息不能越过旧消息，也不会重复发送。
- 断线重试仍以同一 ID 幂等，送达结果不明时不擅自再次发送。

## Windows 普通发送绕过队列修复

### 根因

共享队列服务把 Windows 平台的普通提交配置为允许 `turn/steer`。因此当前回复仍在运行时，Windows 会把普通发送直接插入当前轮次；Linux 则保留在队列，造成相同操作在不同系统上表现不一致。

### 修复约束

- 普通发送在任何平台遇到活动回复都只进入队列，保持 FIFO。
- 只有用户明确点击排队消息的“立即发送”时才允许 `turn/steer` 当前轮次。
- 空闲会话仍由统一提交接口立即启动，不额外显示等待队列。
- 增加 Windows 回归测试，防止平台判断再次改变普通发送语义。
